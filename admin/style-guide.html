Buttons

One primary action per screen area. Use btn--small inside tables, toolbars and card headers.

Add / Remove outside a table: icon and word

Add / Remove in a table row: icon only

The rule: inside a table row, icon only (icon-btn, with aria-label and title); everywhere else, icon plus the word in a button: btn btn--add (green) for Add and Follow, btn btn--danger (red outline) for Remove and Unfollow, with solidIcon('add' | 'addAll' | 'follow' | 'remove' | 'unfollow', 16) from lib.js in front of the word. Tag chips are the one exception and stay icon-only. Delete of a whole record is a red btn--danger button with the trash icon and the word. Anything that removes or deletes must ask confirm() first, naming the thing removed. Add actions that touch many records (like all covers) confirm too.

Do use a real <button type="button"> for actions and <a> only for navigation.

Don’t put an email address in a list as a link. Use the small Email button, which opens the compose box.

Tables

Every list is an .admin-table inside .admin-table-wrap. The header gets the cream band and every other row is striped automatically. Do not add your own row colors except for a row state (overdue, merge).

Status & pills

Pills carry text, so they never rely on color alone. One component, .pill, with a tone named for its meaning: pill--open, --ordered, --done, --warn, --off, --accent, --danger, --super. Statuses that mean the same thing share a tone (e.g. pill--picked_up and pill--available are both “done”), so a status can use its own name as the modifier.

Status icons

Compact solid icons in list tables. An icon appears only when something needs attention, so a healthy row has none. Red means staff should act; amber (is-minor) is a minor issue. Always give each a title and an aria-label. Never show positive states (has account, email on) as icons. Icons are filled shapes: .is-solid fills every path and cuts holes with even-odd fill, so draw details as sub-paths of the same path rather than as strokes.

Spacing & utilities

Use the --sp-* scale (2, 4, 6, 8, 10, 12, 14, 16, 20, 24, 32 px), the --radius-* steps and the status colors (--danger, --success, --info, --stripe) from base.css instead of bare numbers and hex codes. For one-off spacing or layout, use a utility class instead of style="". Utilities sit at the end of admin.css and always win.

Patterns

  • Where code lives: shared components in admin/base.css and admin/admin.css; one screen per file in admin/sections/; helpers (esc, toast, openDialog, sortableTable, formatPhone, withCustomers) in admin/lib.js.
  • Always escape text put into markup with esc().
  • Customer details: show a customer’s current name, phone and email, not what an order was placed with. Use withCustomers(sb, orders).
  • Accessibility: visible labels, role="status" for save results and role="alert" for errors, buttons not links for actions, and at least 36px tap targets (btn--small) in tables.
  • Query builders: never return a Supabase query from an async function; it runs early and breaks .range().
  • New component? Add it to this page in the same commit.
