Buttons

One primary action per screen area. Use btn--small inside tables, toolbars and card headers. On phones every button is at least 48px tall and small ones 44px, so they are always easy to tap. Buttons also have a minimum width (--btn-w, --btn-w-sm for small ones) so Save / Delete pairs and pagers match; a place that wants buttons to shrink to their label or share a row is added to the “Natural-width buttons” list at the end of admin.css.

On long forms the save button stays pinned to the bottom of the screen (here shown in place). It is always the last thing in its form or dialog: a hint or status line goes above it, because anything after it sits under the pinned bar and can’t be read.

Do use a real <button type="button"> for actions and <a> only for navigation. A link that looks like a button (such as View QR code) is an <a class="btn">.

Don’t put an email address in a list as a link. Use the small Email button, which opens the compose box.

Forms

Every input, select and search box is the same height (--field-h, 44px). Wrap each control in .field with a visible <label>. Group fields in a form-grid; form-grid--pairs puts short fields two to a row and .span-2 (or .field--full) keeps a field on the whole row.

Fields in a pairs grid

Hint under a field: small and muted.

On/off switch

For a setting that is either on or off. Build it with switchHtml(label, { name, checked }) from lib.js: a checkbox with role="switch" and its words beside it, on the green --success fill when on, with a 44px touch area and the ordinary focus ring. Change the words with the state (“Chat is on” / “Chat is off”). A switch on its own screen saves the moment it is flipped and says so in a toast, going back if the save fails; a switch inside a settings form waits for Save like every other field there. Use a plain checkbox for “also do this” options in a list of choices.

Fill-in button under the fields it reads

A ghost small button that fills blank fields from somewhere else (Edit Title's “Fill in from PRH”, master catalog only), on a full row right after the fields it reads, with its status beside it and a hint saying what it changes. It never replaces what's typed, and the form still needs Save.

Each field's buttons carry its label for screen readers ("Upload… Logo"), as several image fields often share a screen.

Menu item with a count badge

The menu shows a count for work waiting on staff on every screen: the Chat item counts chats with unread visitor messages (admin/chat-alerts.js), the Surveys item counts survey responses nobody has read yet (admin/survey-alerts.js), and the Events item counts event signups nobody has looked at yet (admin/event-alerts.js). The badge sits at the end of the row and carries hidden words for screen readers (“2 unread chats”). The phone menu button (data-nav-total) shows the total of every badge, since the menu itself is folded away there. A badge clears when the work is done: opening the chat reads it, and opening a survey’s Results reads its responses, and opening Events → Event Signups (or one event’s signups) reads them. The unread chat count also goes first in the browser tab’s title, “(2) Dashboard · Staff · …”. Don’t add a badge for things that are merely new; only for things someone has to answer or read. Inside the screen, the same count shows where it applies: a pill--new (“3 new”) by a survey’s answer count in the list, and an admin-tab__badge on its Results tab; for events, a pill--new on each new signup, “2 new” in its event’s fold and a badge on the Event Signups tab. Dashboard → Needs Attention lists the shop-wide total with a View button.

The menu’s groups fold under their headings (admin-nav__heading with aria-expanded). Pull List starts open; Website and Utilities start folded, set in admin/index.html. Opening or folding a group is remembered on the device (admin-nav-groups in localStorage), and the group holding the open screen always opens so the current item is never hidden. Utilities (Import Titles, Settings, Locations, Staff, Backup, Restore) is for owners only: the group carries data-owner-only and stays hidden for staff, and its screens other than Staff are in OWNER_ONLY in admin.js, so a typed link goes to the Dashboard instead. Staff reach their own My Account from the header’s account menu (the circle with their initial).

  • Phone numbers use formatPhone() from lib.js. Emails are the small Email button, not raw addresses.

Status icons

Compact solid icons in list tables. An icon appears only when something needs attention, so a healthy row has none. Red means staff should act; amber (is-minor) is a minor issue. On the Customers list a Fix button follows only the problems fixed by editing the customer’s details (no address while arrivals ship, no email, a first or last name missing, no phone); those customers, and ones with unlinked guest orders, make up the Needs Attention tab. Past pickup and emails switched off keep their red icon but get no Fix button. Always give each a title and an aria-label. Never show positive states (has account, email on) as icons. Icons are filled shapes: .is-solid fills every path and cuts holes with even-odd fill, so draw details as sub-paths of the same path rather than as strokes.

Panels & folds

A panel is a white card. A fold is a card with a slate header band; if you click the band it opens and closes. Every header, open-and-close or always-open, is the same band: at least 52px tall (--tap-head), square at the bottom while its body shows.

Screen top: title row, How this works, tabs, then everything else

Every screen starts in this order. (1) The title row: the h1 and at most two buttons on the right, like Titles. A screen with no buttons can use a bare h1: it takes the same height and gap as a title row with buttons, so the hint and tabs start at the same place on every screen. (2) “How this works”, right under the title and above the tabs. Every screen has one. One hint for the whole screen is ${hintFold(…)}. When each tab has its own, put ${hintSlot()} there and pass the texts to setupTabs(el, key, fallback, onShow, { tab: html }), or call setHint(el, html) when a view draws itself. (3) The tabs. (4) Everything else (status lines, filters, announcements, export and print, more buttons) goes below the tabs. A form's own hint inside a fold can stay with its form. consistency.test.js checks the order and the two-button limit.

Dialogs

Open with openDialog(title, bodyHtml, { wide }) from lib.js. It builds a native <dialog> with this structure. The dialog__head (title and close ✕) is sticky: it stays at the top while a long dialog scrolls, so it can always be closed. Screen patterns

Layouts that belong to one screen. They are built from the pieces above; reuse the piece, not the screen's own class, when something similar is needed elsewhere.

  • Titles list (sections/titles.js, .titles-table): on phones each title is a grid card (cover, title, dates, status select, Edit, three flags) instead of a cards list, because the cover spans three lines. Dates are .tt-datelink buttons that filter by that week. The title's name is a .tt-datelink button too: it opens the read-only Title Info dialog (.title-info, laid out like the shop’s title details; see Dialogs).
  • Customers list (sections/customers.js, .cust-list): the last column, Status (.col-cust-status), is right-aligned so its icons and Fix button line up at the end of each row; on a phone card the status line starts at the left like the rest of the card.
  • Customer pull list (sections/customers.js, .cust-lines): grouped by Ready for pickup / Open & ordered / Not ordered / Past, one tbody.cust-lines__body each, so stripes come from tr.is-alt, not :nth-child. When more than one group has titles, each starts with a .cust-lines__group heading row in the accent color (--brand-accent with --on-accent) so the groups stand out going down the list. The heading is a .cust-lines__toggle button with aria-expanded and a chevron that folds its group (is-folded hides the rows under it). Past starts folded, and each group’s choice is remembered on the device. It stacks below 1200px (the side menu takes room).
  • Reservations: an order opens under its row (sections/reservations.js): the row gets is-open (blue) and its View button aria-expanded="true", and a tr.order-expand under it holds .order--inline with its own title list (.order__lines, alternate rows in the light blue). On phones that title list is a grid below 600px.
  • Place Order cutoffs (.fold--compact[data-foc]): one fold per order cutoff, its count in the header note and the Mark ordered button at the top of the body. See Panels & folds.
  • Place Order, Past Orders, Received and Re-order: customers under a title (tr.toorder__people): click the Customers count (a .link-button) to open a striped row under the title listing who reserved it, in columns (.toorder__list); Past Orders and Received add where each line stands.
  • Re-order (renderReorders in sections/reservations.js): titles ordered after their cutoff, built from the same pieces as Place Order: a static fold to find any title (.cust-search, .cust-results) and who it's for, the distributor tools panel (.order-tools), then To Re-order and On Order folds (.fold--compact) with the Mark ordered button at the top. An order's kind pill: pill--pull Pull list, pill--info Re-order, pill--off Guest order.
  • Dashboard → Most Reserved (.dash-top): rank, a bigger cover, then title, Out date and copies; a grid card on phones.
  • Series merge (sections/series.js): tick series to merge and pick one to keep; rows show is-merge / is-keep (see Row states).
  • QR codes (sections/qr.js, .qr-item): a fold per code with its form beside a 260px preview (role="img"); a code opened from a link (#qr/<slug>) flashes once.
  • Survey questions (sections/surveys.js, .sq-head): a fold per question with the answer type under the question in its header.

Do add a screen here when you give it a layout of its own, with the file, the class and why the shared pieces didn't fit.

Spacing & utilities

Use the --sp-* scale for margin, padding and gap, the --radius-* steps for corners, and the status colors from base.css. Do not write bare pixel values: consistency.test.js rejects a px or rem margin, padding, gap or corner. Allowed besides: 0, auto, em / ch / % (sizes relative to the text), a negative offset that lines edges up, and anything inside calc().

Rules

  • Where code lives: shared components in admin/base.css and admin/admin.css; one screen per file in admin/sections/; helpers (esc, toast, openDialog, hintFold, sortableTable) in admin/lib.js.
  • One look for each job: headers are the slate band; actions are buttons from the Buttons section; states are pills. If you need something that is not here, add it here first.
  • Breakpoints: phone up to 599px, tablet 600–899px, desktop from 900px, wide from 1200px. Small tablets split at 700px and the narrowest phones at 380px. Use max-width: 599/699/899/1199px or min-width: 600/700/900/1200px; consistency.test.js rejects any other width.
  • Tap targets: --tap-btn (48px) for buttons and --tap (44px) for small buttons and fields on phones; clickable fold headers --tap-head (52px).
  • Always escape text put into markup with esc().
  • Ids: make a label's for / field id pair with uid('prefix') from lib.js, not Math.random().
  • Templates: start a new line at each block tag (<div>, <p>, <tr>, <td>, <option>…), never between inline ones (buttons, spans, links), where a line break shows as a space.
  • No fixed inline styles: a look is a class in admin.css (or a helper such as font-mono). A style="…" in a screen is only for a value worked out at run time, such as a bar's width; consistency.test.js rejects any other. A solid icon's cut-out is an even-odd hole in its path, not a white shape.
  • Customer details: show a customer’s current name, phone and email, not what an order was placed with. Use withCustomers(sb, orders).
  • Accessibility: visible labels, role="status" for save results and role="alert" for errors, buttons not links for actions, and text that keeps at least 4.5:1 contrast in both themes. Field borders and focus rings keep 3:1; focus rings use --focus. Never make a whole screen a live region, and never put a button inside a <summary>. Tab rows (role="tablist") get arrow keys from admin.js.
  • Query builders: never return a Supabase query from an async function; it runs early and breaks .range().
  • New component? Add it to this page in the same commit. npm test (admin/consistency.test.js) fails if a shared component is missing here, if text contrast drops below 4.5:1 in either theme, if a screen adds a one-off button height, a raw color, a bare spacing value or corner, or uses --border as a color, or if a button or pill class has no style.

Deliberate exceptions

  • Filter labels on the Titles screen are a little smaller than other field labels, so seven filters fit on one row.
  • The up and down arrows on FAQ questions are fixed-width icon buttons rather than the standard small button.
  • The Edit button in the Titles list on phones has tighter side padding so it fits beside the cover and status.
